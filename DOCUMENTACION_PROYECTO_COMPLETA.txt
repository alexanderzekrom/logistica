FASE 1: INICIO Y DEFINICIÓN
================================================================================

1.1 INTRODUCCIÓN
-----------------
Este documento presenta el desarrollo completo del "Sistema de Logística y Envíos", 
una plataforma web integral diseñada para la gestión, asignación y rastreo en tiempo 
real de entregas de paquetes en El Salvador. 

El documento está dirigido al docente de la asignatura Infraestructura y Cómputo en 
la Nube, así como a los equipos de desarrollo (Grupo A - Backend y Grupo B - Frontend) 
que participaron en la construcción del sistema bajo una arquitectura desacoplada.

El proyecto consiste en una aplicación web que permite a tres tipos de usuarios 
(Administradores, Conductores y Clientes) interactuar sobre una misma base de datos 
para gestionar el ciclo de vida completo de los pedidos de envío, desde su registro 
hasta su entrega final, con visualización geográfica mediante mapas interactivos.

1.2 OBJETIVOS
-------------

1.2.1 Objetivo General
Desarrollar e implementar un sistema de logística y envíos desacoplado en arquitectura 
cliente-servidor, desplegado en infraestructura cloud IaaS (AWS EC2), que permita la 
gestión eficiente de pedidos, asignación de recursos y rastreo en tiempo real de 
entregas en El Salvador.

1.2.2 Objetivos Específicos
- Diseñar e implementar una API REST backend con FastAPI que exponga endpoints para 
  la gestión de clientes, conductores, vehículos y pedidos.
- Desarrollar una interfaz web frontend con React y TypeScript que permita la interacción 
  de usuarios según sus roles (ADMIN, CONDUCTOR, CLIENTE).
- Implementar un sistema de autenticación basado en JWT con control de acceso por roles.
- Diseñar una base de datos relacional MySQL que soporte el modelo de datos del sistema 
  logístico.
- Configurar la infraestructura en AWS EC2 con instancias independientes para backend 
  y frontend, siguiendo el modelo IaaS.
- Implementar comunicación segura entre frontend y backend mediante Security Groups 
  en AWS.
- Integrar mapas interactivos (MapLibre GL) para visualización geográfica de pedidos.
- Establecer reglas de negocio que controlen los flujos de estado de los pedidos.

1.3 JUSTIFICACIÓN
-----------------
La necesidad de este sistema surge de la creciente demanda de servicios de logística 
y entrega en El Salvador, donde muchas empresas aún gestionan sus procesos de forma 
manual o con sistemas desactualizados que no permiten rastreo en tiempo real.

El impacto y beneficio de este proyecto incluyen:
- **Eficiencia Operativa**: Automatización de la asignación de conductores y vehículos 
  a pedidos, reduciendo tiempos de gestión manual.
- **Visibilidad en Tiempo Real**: Clientes y administradores pueden rastrear la ubicación 
  de los pedidos mediante mapas interactivos.
- **Control de Calidad**: Implementación de estados de pedido que permiten identificar 
  incidencias y tomar acciones correctivas.
- **Escalabilidad**: Arquitectura desacoplada en AWS EC2 que permite escalar frontend 
  y backend independientemente según la demanda.
- **Seguridad**: Implementación de autenticación JWT y restricciones de acceso por roles, 
  además de Security Groups en AWS que protegen la comunicación entre componentes.
- **Experiencia de Usuario**: Interfaz web moderna y responsiva que facilita la 
  interacción de los diferentes tipos de usuarios.

Para la institución educativa, este proyecto representa una aplicación práctica de 
conceptos de computación en la nube, arquitectura de software y desarrollo web, 
preparando a los estudiantes con experiencia real en despliegue de aplicaciones 
en infraestructura cloud profesional.

1.4 ALCANCES Y LIMITACIONES
----------------------------

1.4.1 Alcances
El sistema incluirá las siguientes funcionalidades:
- Gestión completa de clientes (CRUD: Crear, Leer, Actualizar, Eliminar)
- Gestión completa de conductores (CRUD)
- Gestión completa de vehículos (CRUD)
- Gestión de pedidos con control de estados (PENDIENTE, ASIGNADO, EN_CAMINO, 
  ENTREGADO, INCIDENCIA, CANCELADO)
- Sistema de autenticación con tres roles: ADMIN, CONDUCTOR, CLIENTE
- Asignación de conductores y vehículos a pedidos (solo ADMIN)
- Visualización de pedidos filtrados por rol de usuario
- Actualización de estado de pedidos con validación de reglas de negocio
- Cancelación de pedidos por clientes (solo en estado PENDIENTE)
- Visualización geográfica de pedidos en mapas interactivos
- Despliegue en AWS EC2 con instancias separadas para frontend y backend
- Comunicación segura entre componentes mediante Security Groups
- Persistencia de datos en base de datos MySQL

1.4.2 Limitaciones
El sistema NO incluirá:
- Procesamiento de pagos en línea
- Integración con sistemas de mensajería externos (SMS, email)
- Cálculo automático de rutas óptimas de entrega
- Historial completo de cambios de estado (auditoría detallada)
- Reportes estadísticos o analíticos avanzados
- Aplicación móvil nativa (solo interfaz web responsiva)
- Integración con GPS en tiempo real de vehículos
- Sistema de notificaciones push
- Gestión de inventario de paquetes
- Cálculo de costos de envío
- Múltiples idiomas (solo español)
- Carga masiva de datos (importación/exportación)

2.3 CASOS DE USO
----------------

CU01: Iniciar Sesión
- Actor: Usuario (ADMIN, CONDUCTOR, CLIENTE)
- Descripción: El usuario ingresa sus credenciales (username y password) para acceder al sistema.
- Precondiciones: El usuario debe estar registrado en la base de datos.
- Flujo Principal:
  1. El usuario ingresa username y password en el formulario de login.
  2. El sistema valida las credenciales contra la base de datos.
  3. Si las credenciales son correctas, el sistema genera un token JWT.
  4. El sistema redirige al usuario al panel correspondiente según su rol.
- Postcondiciones: El usuario autenticado accede al sistema con su rol asignado.

CU02: Registrar Pedido (Cliente)
- Actor: CLIENTE
- Descripción: El cliente registra un nuevo pedido de envío con ubicación geográfica.
- Precondiciones: El cliente debe estar autenticado con rol CLIENTE.
- Flujo Principal:
  1. El cliente accede al formulario de creación de pedido.
  2. El cliente selecciona la ubicación en el mapa interactivo.
  3. El cliente ingresa la dirección de entrega.
  4. El sistema valida los datos ingresados.
  5. El sistema crea el pedido con estado PENDIENTE.
  6. El sistema confirma la creación del pedido.
- Postcondiciones: El pedido queda registrado en estado PENDIENTE sin asignación de recursos.

CU03: Asignar Recursos a Pedido (Admin)
- Actor: ADMIN
- Descripción: El administrador asigna un conductor y un vehículo a un pedido pendiente.
- Precondiciones: El administrador debe estar autenticado con rol ADMIN. El pedido debe estar en estado PENDIENTE.
- Flujo Principal:
  1. El administrador selecciona un pedido de la lista.
  2. El administrador elige un conductor disponible.
  3. El administrador elige un vehículo disponible.
  4. El sistema valida la asignación.
  5. El sistema actualiza el pedido a estado ASIGNADO.
  6. El sistema confirma la asignación.
- Postcondiciones: El pedido pasa a estado ASIGNADO con conductor y vehículo asignados.

CU04: Actualizar Estado de Pedido (Conductor)
- Actor: CONDUCTOR
- Descripción: El conductor actualiza el estado de un pedido asignado durante su jornada.
- Precondiciones: El conductor debe estar autenticado con rol CONDUCTOR. El pedido debe estar asignado a su ID.
- Flujo Principal:
  1. El conductor accede a su panel de "Mi Jornada".
  2. El conductor selecciona un pedido de su lista.
  3. El conductor selecciona el nuevo estado (EN_CAMINO, ENTREGADO, INCIDENCIA).
  4. El sistema valida la transición de estado según reglas de negocio.
  5. El sistema actualiza el estado del pedido.
  6. El sistema confirma la actualización.
- Postcondiciones: El estado del pedido se actualiza según la acción del conductor.

CU05: Cancelar Pedido (Cliente)
- Actor: CLIENTE
- Descripción: El cliente cancela un pedido que aún no ha sido asignado.
- Precondiciones: El cliente debe estar autenticado con rol CLIENTE. El pedido debe estar en estado PENDIENTE.
- Flujo Principal:
  1. El cliente accede a su lista de pedidos.
  2. El cliente selecciona un pedido en estado PENDIENTE.
  3. El cliente confirma la cancelación.
  4. El sistema valida que el pedido esté en estado PENDIENTE.
  5. El sistema actualiza el pedido a estado CANCELADO.
  6. El sistema confirma la cancelación.
- Postcondiciones: El pedido pasa a estado CANCELADO y no puede ser modificado.

CU06: Gestionar Clientes (Admin)
- Actor: ADMIN
- Descripción: El administrador realiza operaciones CRUD sobre la tabla de clientes.
- Precondiciones: El administrador debe estar autenticado con rol ADMIN.
- Flujo Principal:
  1. El administrador accede a la sección de Clientes.
  2. El administrador puede crear, leer, actualizar o eliminar clientes.
  3. El sistema valida los datos ingresados.
  4. El sistema persiste los cambios en la base de datos.
- Postcondiciones: La información de clientes se actualiza según la operación realizada.

CU07: Visualizar Mapa de Pedidos (Todos los roles)
- Actor: ADMIN, CONDUCTOR, CLIENTE
- Descripción: El usuario visualiza la ubicación geográfica de los pedidos en un mapa interactivo.
- Precondiciones: El usuario debe estar autenticado. Los pedidos se filtran según el rol.
- Flujo Principal:
  1. El usuario accede a la sección de Mapa.
  2. El sistema carga los pedidos correspondientes al rol del usuario.
  3. El sistema muestra marcadores en el mapa para cada pedido.
  4. El usuario puede interactuar con los marcadores para ver detalles.
- Postcondiciones: El usuario visualiza la ubicación geográfica de los pedidos accesibles.

3.1 ARQUITECTURA DE HARDWARE/RED (AWS)
---------------------------------------

Topología de Instancias EC2:

Internet
    |
    v
[EC2 FRONTEND] (IP Pública con Elastic IP)
    | - Puerto 80 (HTTP) - Abierto a Internet
    | - Puerto 443 (HTTPS) - Abierto a Internet
    | - Puerto 22 (SSH) - Restringido a IP administrativa
    |
    | - Contenedor Docker: Nginx (Reverse Proxy)
    | - Contenedor Docker: React Frontend (puerto interno 3000)
    |
    v (Comunicación por IP privada)
[EC2 BACKEND] (IP Privada en VPC)
    | - Puerto 8000 (FastAPI) - Solo accesible desde SG-FRONTEND
    | - Puerto 22 (SSH) - Restringido a IP administrativa
    |
    | - Contenedor Docker: FastAPI Backend (puerto 8000)
    | - Contenedor Docker: MySQL Database (puerto interno 3306)
    |
    v
[Volumen Docker: Persistencia de datos MySQL]

Security Groups:

SG-FRONTEND:
- Regla de entrada: TCP 80 desde 0.0.0.0/0 (Internet)
- Regla de entrada: TCP 443 desde 0.0.0.0/0 (Internet)
- Regla de entrada: TCP 22 desde [IP administrativa]
- Regla de salida: Todo el tráfico

SG-BACKEND:
- Regla de entrada: TCP 8000 desde SG-FRONTEND
- Regla de entrada: TCP 22 desde [IP administrativa]
- Regla de salida: Todo el tráfico

Flujo de Comunicación:
1. Usuario accede via HTTP/HTTPS a la IP pública del EC2 FRONTEND
2. Nginx en FRONTEND recibe la petición
3. Si la ruta es /api/*, Nginx hace proxy a la IP privada del BACKEND puerto 8000
4. Si la ruta es /, Nginx sirve la aplicación React
5. FastAPI en BACKEND procesa la petición y consulta MySQL
6. MySQL responde a FastAPI
7. FastAPI retorna la respuesta a Nginx
8. Nginx retorna la respuesta al usuario

3.2 ARQUITECTURA DE SOFTWARE
-----------------------------

Patrón Arquitectónico: Cliente-Servidor Desacoplado con API REST

Justificación:
- **Desacoplamiento**: Frontend y backend son aplicaciones independientes que se comunican 
  únicamente a través de HTTP/JSON. Esto permite desarrollo paralelo por equipos diferentes 
  (Grupo A y Grupo B) y escalabilidad independiente.
- **API REST**: Estándar ampliamente adoptado que facilita la integración, es stateless, 
  cacheable y utiliza métodos HTTP estándar (GET, POST, PUT, DELETE).
- **Separación de Responsabilidades**: Backend se enfoca en lógica de negocio y persistencia 
  de datos. Frontend se enfoca en presentación y experiencia de usuario.
- **Escalabilidad**: Cada componente puede escalar horizontalmente según la demanda. 
  Se pueden agregar más instancias de frontend para manejar más usuarios, o más instancias 
  de backend para procesar más peticiones API.
- **Mantenibilidad**: Cambios en el frontend no afectan al backend y viceversa, siempre 
  que se mantenga el contrato de la API.

Capas de la Arquitectura:

Backend (FastAPI):
- Capa de Rutas: Endpoints HTTP que reciben peticiones
- Capa de Lógica de Negocio: Validaciones, reglas de negocio, procesamiento
- Capa de Acceso a Datos: SQLAlchemy ORM para interactuar con MySQL
- Capa de Seguridad: Autenticación JWT, autorización por roles

Frontend (React):
- Capa de Presentación: Componentes UI con TypeScript
- Capa de Estado: Gestión de estado local y global
- Capa de Servicios: Cliente API para comunicación con backend
- Capa de Navegación: Enrutamiento entre páginas

3.3.2 Diccionario de Datos

Tabla: USUARIOS
- id_usuario: INT AUTO_INCREMENT PRIMARY KEY
  * Descripción: Identificador único del usuario
  * Restricciones: No nulo, auto-incremental
- username: VARCHAR(50) NOT NULL UNIQUE
  * Descripción: Nombre de usuario para login
  * Restricciones: No nulo, único, máximo 50 caracteres
- password_hash: VARCHAR(255) NOT NULL
  * Descripción: Contraseña encriptada con bcrypt
  * Restricciones: No nulo, máximo 255 caracteres
- rol: ENUM('ADMIN', 'CONDUCTOR', 'CLIENTE') NOT NULL
  * Descripción: Rol de acceso del usuario
  * Restricciones: No nulo, solo valores permitidos
- id_ref: INT NULL
  * Descripción: ID de referencia en tabla clientes o conductores
  * Restricciones: Nulo para ADMIN, referencia a cliente o conductor para otros roles
- created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  * Descripción: Fecha y hora de creación del registro
  * Restricciones: Automático

Tabla: CLIENTES
- id_cliente: INT AUTO_INCREMENT PRIMARY KEY
  * Descripción: Identificador único del cliente
  * Restricciones: No nulo, auto-incremental
- nombre: VARCHAR(100) NOT NULL
  * Descripción: Nombre completo del cliente
  * Restricciones: No nulo, máximo 100 caracteres
- telefono: VARCHAR(20) NOT NULL
  * Descripción: Número de teléfono del cliente
  * Restricciones: No nulo, máximo 20 caracteres
- email: VARCHAR(100) NOT NULL UNIQUE
  * Descripción: Correo electrónico del cliente
  * Restricciones: No nulo, único, máximo 100 caracteres
- direccion: TEXT NOT NULL
  * Descripción: Dirección física del cliente
  * Restricciones: No nulo

Tabla: CONDUCTORES
- id_conductor: INT AUTO_INCREMENT PRIMARY KEY
  * Descripción: Identificador único del conductor
  * Restricciones: No nulo, auto-incremental
- nombre: VARCHAR(100) NOT NULL
  * Descripción: Nombre completo del conductor
  * Restricciones: No nulo, máximo 100 caracteres
- licencia: VARCHAR(50) NOT NULL UNIQUE
  * Descripción: Número de licencia de conducir
  * Restricciones: No nulo, único, máximo 50 caracteres
- telefono: VARCHAR(20) NOT NULL
  * Descripción: Número de teléfono del conductor
  * Restricciones: No nulo, máximo 20 caracteres

Tabla: VEHICULOS
- id_vehiculo: INT AUTO_INCREMENT PRIMARY KEY
  * Descripción: Identificador único del vehículo
  * Restricciones: No nulo, auto-incremental
- placa: VARCHAR(20) NOT NULL UNIQUE
  * Descripción: Número de placa del vehículo
  * Restricciones: No nulo, único, máximo 20 caracteres
- tipo: VARCHAR(50) NOT NULL
  * Descripción: Tipo de vehículo (ej. Camión, Panel Van)
  * Restricciones: No nulo, máximo 50 caracteres
- capacidad: VARCHAR(50) NOT NULL
  * Descripción: Capacidad de carga del vehículo
  * Restricciones: No nulo, máximo 50 caracteres

Tabla: PEDIDOS
- id_pedido: INT AUTO_INCREMENT PRIMARY KEY
  * Descripción: Identificador único del pedido
  * Restricciones: No nulo, auto-incremental
- id_cliente: INT NOT NULL
  * Descripción: ID del cliente que realiza el pedido
  * Restricciones: No nulo, FK a clientes(id_cliente), ON DELETE RESTRICT
- id_conductor: INT NULL
  * Descripción: ID del conductor asignado al pedido
  * Restricciones: Nulo, FK a conductores(id_conductor), ON DELETE SET NULL
- id_vehiculo: INT NULL
  * Descripción: ID del vehículo asignado al pedido
  * Restricciones: Nulo, FK a vehiculos(id_vehiculo), ON DELETE SET NULL
- direccion: TEXT NOT NULL
  * Descripción: Dirección de entrega del pedido
  * Restricciones: No nulo
- latitud: DECIMAL(10, 8) NOT NULL
  * Descripción: Coordenada de latitud para el mapa
  * Restricciones: No nulo, precisión de 10 dígitos, 8 decimales
- longitud: DECIMAL(11, 8) NOT NULL
  * Descripción: Coordenada de longitud para el mapa
  * Restricciones: No nulo, precisión de 11 dígitos, 8 decimales
- estado: ENUM('PENDIENTE', 'ASIGNADO', 'EN_CAMINO', 'ENTREGADO', 'INCIDENCIA', 'CANCELADO') DEFAULT 'PENDIENTE'
  * Descripción: Estado actual del pedido en el flujo de entrega
  * Restricciones: No nulo, solo valores permitidos, default PENDIENTE
- created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  * Descripción: Fecha y hora de creación del pedido
  * Restricciones: Automático

Backend:
- **Lenguaje**: Python 3.12+

- **Servidor ASGI**: Uvicorn 0.27.0
  * Justificación: Servidor ASGI de alto rendimiento compatible con FastAPI, ideal

- **ORM**: SQLAlchemy 2.0.25
  * Justificación: ORM maduro y potente que abstrae la complejidad de SQL, permite

  * Justificación: Driver MySQL puro en Python, no requiere dependencias de C,

  * Justificación: Biblioteca de validación de datos con soporte para tipado, 
    integración nativa con FastAPI, generación automática de schemas JSON.

  * Justificación: python-jose para manejo de tokens JWT (codificación/decodificación),

  * Justificación: Superset de JavaScript con tipado estático que previene errores

  * Justificación: Biblioteca UI más popular del mundo, basada en componentes,

4. Tipo: RSA
5. Formato: .pem

Paso 2: Lanzar Instancia EC2 Backend
1. AWS Console -> EC2 -> Instances -> Launch Instance
2. Nombre: logistica-backend
3. AMI: Ubuntu Server 22.04 LTS
4. Instance Type: t2.micro (o t3.micro)
5. Key Pair: logistica-backend-key
6. Network Settings:
   - VPC: Default
   - Subnet: Default
   - Auto-assign Public IP: Enable
   - Security Group: Crear nuevo SG-BACKEND
     * SSH (22): From My IP
     * Custom TCP (8000): From SG-FRONTEND (crear después)
7. Storage: 20 GB GP2
8. Click en "Launch Instance"

Paso 3: Crear Security Group Backend
1. EC2 -> Security Groups -> Create Security Group
2. Nombre: sg-backend
3. Descripción: Security Group para backend logística
4. Reglas de entrada:
   - Type: SSH, Port: 22, Source: [Tu IP pública]/32
   - Type: Custom TCP, Port: 8000, Source: sg-frontend (crear después)
5. Click en "Create Security Group"
6. Asociar este SG a la instancia backend si no se hizo en el lanzamiento

Crear archivo /etc/nginx/sites-available/logistica:
```nginx
server {
    listen 80;
    server_name <TU_DOMINIO_O_IP>;  # ej. app.tudominio.com o IP pública

    # Proxy para API hacia backend
    location /api/ {
        proxy_pass http://<IP_PRIVADA_BACKEND>:8000/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Servir frontend React
    location / {
        proxy_pass http://frontend:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Activar configuración:

6.1 CONCLUSIONES Y RECOMENDACIONES
----------------------------------

6.1.1 Conclusiones

El desarrollo del Sistema de Logística y Envíos ha permitido aplicar de manera 
práctica los conceptos de infraestructura en la nube, arquitectura de software 
desacoplada y desarrollo web moderno. A través de las 6 fases del proyecto, 
se lograron los siguientes resultados:

1. **Arquitectura Desacoplada Exitosa**: La separación entre frontend (React) 
   y backend (FastAPI) funcionó correctamente, permitiendo desarrollo paralelo 
   y despliegue independiente en instancias EC2 separadas.

2. **Infraestructura Cloud IaaS**: La implementación en AWS EC2 siguió el modelo 
   IaaS requerido, proporcionando control completo sobre el sistema operativo 
   y configuración de las instancias.

3. **Seguridad Implementada**: Los Security Groups de AWS restringieron correctamente 
   el acceso, permitiendo solo comunicación autorizada entre componentes. 
   La autenticación JWT y encriptación de passwords con bcrypt protegieron 
   el acceso a la aplicación.

4. **API REST Funcional**: FastAPI con SQLAlchemy proporcionó una API robusta 
   con validación automática de datos, documentación interactiva (Swagger) 
   y rendimiento adecuado.

5. **Interfaz de Usuario Moderna**: React con TypeScript y TailwindCSS permitió 
   crear una interfaz responsiva y atractiva con excelente experiencia de usuario.

6. **Integración de Mapas**: MapLibre GL proporcionó visualización geográfica 
   interactiva sin dependencias de servicios propietarios, utilizando datos 
   de OpenStreetMap.

7. **Persistencia de Datos**: MySQL con volúmenes Docker aseguró la persistencia 
   de datos tras reinicios de contenedores.

8. **Escalabilidad**: La arquitectura permite escalar frontend y backend 
   independientemente agregando más instancias EC2 según la demanda.

6.1.2 Lecciones Aprendidas

1. **Importancia de la Planificación**: La documentación previa (DER, casos de uso, 
   requerimientos) facilitó significativamente el desarrollo y evitó 
   retrabajos.

2. **Gestión de Secrets**: Las variables de entorno y archivos .env son 
   críticos para la seguridad. No deben incluirse en el repositorio Git.

3. **Configuración de AWS**: Los Security Groups requieren configuración 
   cuidadosa. Un error puede dejar puertos expuestos o bloquear comunicación 
   legítima.

4. **Docker Simplifica Despliegue**: El uso de Docker garantiza consistencia 
   entre entornos de desarrollo y producción.

5. **Comunicación Frontend-Backend**: El reverse proxy Nginx es esencial 
   para orquestar comunicación entre componentes en arquitectura desacoplada.

6. **Pruebas Integrales**: Es fundamental probar no solo la funcionalidad 
   individual, sino también la integración entre componentes y la infraestructura.

7. **Documentación Técnica**: La documentación de despliegue es crítica 
   para replicación y mantenimiento del sistema en producción.

6.1.3 Recomendaciones

1. **Mejoras de Seguridad**:
   - Implementar HTTPS con SSL/TLS en producción (recomendado usar AWS ACM)
   - Rotar regularmente las credenciales de base de datos y secrets
   - Implementar rate limiting en la API para prevenir ataques
   - Utilizar AWS Secrets Manager para gestionar secrets en lugar de .env
   - Implementar logging y monitoreo con AWS CloudWatch

2. **Mejoras de Arquitectura**:
   - Migrar de EC2 a AWS Elastic Beanstalk o ECS para orquestación automática
   - Utilizar AWS RDS para MySQL en lugar de contenedor Docker (mejor 
     disponibilidad y backups automáticos)
   - Implementar Application Load Balancer (ALB) para balancear carga 
     entre múltiples instancias frontend
   - Utilizar AWS S3 + CloudFront para servir archivos estáticos del frontend
   - Implementar cache con Redis para sesiones y datos frecuentes

3. **Mejoras de Funcionalidad**:
   - Agregar sistema de notificaciones (email/SMS) para actualizaciones de estado
   - Implementar cálculo de rutas óptimas con API de Google Maps o OSRM
   - Agregar módulo de pagos en línea (Stripe, PayPal)
   - Implementar reportes estadísticos y dashboard analítico
   - Agregar historial de auditoría para cambios de estado
   - Implementar carga masiva de datos (importación CSV/Excel)
   - Desarrollar aplicación móvil nativa (React Native o Flutter)

4. **Mejoras de Experiencia de Usuario**:
   - Implementar modo offline con Service Workers
   - Agregar soporte para múltiples idiomas (i18n)
   - Implementar dark mode
   - Mejorar accesibilidad (WCAG compliance)
   - Agregar tutoriales interactivos para nuevos usuarios

5. **Mejoras de Infraestructura**:
   - Implementar CI/CD con AWS CodePipeline o GitHub Actions
   - Configurar backups automáticos de la base de datos
   - Implementar multi-AZ deployment para alta disponibilidad
   - Configurar auto-scaling groups para escalar automáticamente
   - Implementar blue/green deployments para actualizaciones sin downtime

6. **Mejoras de Código**:
   - Agregar pruebas unitarias con pytest
   - Implementar pruebas de integración
   - Agregar pruebas end-to-end con Playwright o Cypress
   - Implementar linting y formateo automático (ESLint, Prettier, Black)
   - Mejorar manejo de errores y mensajes de usuario
   - Implementar logging estructurado
